# Claude Review: Model-Switching Dashboard

Date: 2026-07-15

## Prompt sent to Claude

Act as a skeptical staff architect reviewing a local-first LLM memory demo before shipment.

The implemented dashboard:

- Replays a committed schema-v2 JSON evidence report for Claude Haiku → Claude Sonnet → Claude Haiku.
- Lets the user import another report through a browser-local file picker; it does not upload the file.
- Does not invoke models or open SQLite from the browser. New live evidence is generated by a Python CLI harness.
- Explicitly says the harness performs memory writes/recall/correction and models only consume supplied context.
- Shows exact memory item count, Unicode character count, UTF-8 byte count, prompt-character share, and bundle-character-budget utilization.
- Shows token count as `ceil(memory characters / 4)` and labels it a tokenizer-independent estimate, not exact provider usage or billing data.
- Animates model switching, compares no-memory baseline to memory-assisted exact-slot accuracy, and shows correction/stale-leak/private-isolation checks.
- Uses randomized synthetic canonical values. The live run passed: baseline 0%, memory-assisted 100%, correction 100%, zero stale leaks, zero private-scope violations. First handoff: 3 items, 486 characters/bytes, ~122 tokens. Return handoff: 5 items, 812 characters/bytes, ~203 tokens.

Architecture decision AD-024 says the dashboard is local evidence replay; exact counts come from the Python harness; token count is approximate; the browser receives neither the database nor credentials.

Review these questions concisely:

1. Is any claim materially misleading, especially “memory copied to another model's context”?
2. Are the measurement definitions defensible and clearly separated between exact and estimated values?
3. Are there security/privacy problems in the replay/import design?
4. Name any ship-blocking issue and any small recommended improvement.

Return sections: Verdict, Ship blockers, Recommended improvements, and wording corrections. Do not propose a large redesign unless required.

Provide the complete review now using only the information above. Do not inspect files and do not describe future actions.

## Claude response

### Verdict

Ship-ready with minor wording fixes. The core claims are defensible: the dashboard is transparent about being a replay of harness-generated evidence, does not claim to move a live SQLite database or credentials into the browser, and clearly labels token count as an estimate. No fabricated capability claims.

### Ship blockers

None identified from the description given.

### Recommended improvements

1. Tighten “memory copied to another model's context.” It could imply persistent transfer or state sharing. Prefer “memory items are re-supplied as context” or “included in the prompt.”
2. Keep the tokenizer-independent caveat next to the token estimate; the characters/4 heuristic is coarse and real tokenizers vary.
3. Label the accuracy and leak metrics as specific to “this run,” not a general guarantee.
4. Put browser-local/no-upload reassurance next to the report file picker.

### Security/privacy assessment

No issues. No model invocation from the browser, no SQLite access from the browser, no credentials in scope, and the import path is local-only. This is a reasonable trust boundary for a demo artifact.

### Wording corrections

- “memory copied to another model's context” → “memory items re-supplied as context to the next model”
- Co-locate “estimate” / “tokenizer-independent” with the token count display.
- Qualify the 100% and zero-leak figures as specific to this run.

## Reconciliation

Accepted all four recommendations. The UI now uses re-supplied/included wording, labels outcomes as “this run,” keeps the estimate caveat adjacent to transfer metrics, and states beside the picker that imported files stay in the browser. No architectural change was required.
