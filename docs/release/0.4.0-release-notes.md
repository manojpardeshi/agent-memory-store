# LLM Memory Store 0.4.0

LLM Memory Store 0.4.0 adds opt-in re-ranked recall. This is the project's first retrieval
improvement confirmed on a held-out dataset from a different source than the one it was tuned on.
The release also fixes two problems found by formally proving the code's safety properties, and
ships those proofs. Default recall behaves exactly as in 0.3.

## Highlights

- **Re-ranked recall (opt-in).** `recall(..., rerank=True)`, `llm-memory recall --rerank`, and MCP
  `rerank: true` re-score the first 20 vector candidates with a small local cross-encoder
  (`Xenova/ms-marco-MiniLM-L-6-v2`, Apache-2.0, about 92 MB, downloaded on first use) and reorder
  them. It helps most where answers need several memories.

  | Data set | Vector | Re-ranked |
  | --- | ---: | ---: |
  | LongMemEval-S development (tuning), questions with all evidence in the top ten | 121 / 174 | 138 / 174 |
  | LoCoMo-10 (held out; frozen rule; one look) | 805 / 1,536 | **924 / 1,536** |

  Every LoCoMo category improved. The cost is about 140 ms more per recall on a laptop CPU, which
  is why re-ranking is off by default.
  - Re-ranking only reorders memories recall already found, so scope isolation is unchanged.
  - It cannot be combined with hybrid recall.
  - `MemoryStore(reranker=...)` accepts your own `FastEmbedReranker`, for example for offline use
    with `local_files_only=True`.
- **Formal proofs.** `proofs/` holds 51 machine-checked Rocq theorems across five components, all
  closed under the global context and independently re-checked by `coqchk`
  (`scripts/check_proofs.sh`):
  - Keyword queries cannot inject FTS5 syntax.
  - Fusion and re-ranking never introduce an item, so scope isolation is preserved.
  - The held-out ledger respects its look budget.
  - `occurred_at` validation is sound.

  Hypothesis property tests check the real code against the same properties. The proofs cover
  models of the code, with every simplification listed in `proofs/README.md`.

## Security and compatibility

- **Patched dependencies.** FastEmbed 0.9.1 with Pillow 13 fixes about 40 Pillow advisories.
  pip-audit reports no known vulnerability in the locked runtime set.
- **Stores open across runtime updates.** A routine ONNX Runtime update could change a store's
  embedding fingerprint by numerical noise alone, making the store refuse to open and silently
  turning off the certified relevance filter. 0.4.0 judges both by behaviour, accepting
  fingerprints measured equivalent (cosine 1.000000, identical retrieval results). Stores created
  under earlier releases now open whichever ONNX Runtime is installed.
  - Details: `docs/architecture/benchmarks/2026-10-27-embedding-runtime-equivalence.md`.

## Fixed

- Hybrid recall's rank-fusion scores are now exact fractions. Exactly equal scores were sometimes
  ordered by float rounding instead of by memory id.
- The held-out look ledger is now locked, so two simultaneous looks cannot both pass the budget.
- `occurred_at` values near the edges of the representable date range raise `ValueError`, not
  `OverflowError`.

## Compatibility

No schema change, and stores from 0.1–0.3 open unchanged. Releases before 0.4.0 still require an
exact fingerprint match, so they cannot open a store whose fingerprint differs from their own
runtime's. Results gain an optional `rerank_score` only when re-ranking is on. Hybrid rankings can
differ from 0.3 only for exactly tied fusion scores.

## Packaging

Python 3.11 or newer. Runtime dependencies: `fastembed>=0.9.1,<1` (was `>=0.8,<1`), a new
`pillow>=13` security floor, and the unchanged `mcp` and `sqlite-vec`. The re-ranker uses FastEmbed.
